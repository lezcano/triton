Reproducers used during analysis:
  checked-in dgrad specialization:
    `python/examples/gluon/02-conv-dgrad.py`:
    `test_op[conv2d_dgrad_fixed-1-384-64-64-384-3-3-1-0]`
  checked-in wgrad specialization:
    `python/examples/gluon/02-conv-wgrad.py`:
    `test_op[conv2d_wgrad_fixed-1-128-64-64-128-1-1-1-0]`
  checked-in MoE specialization:
    `python/examples/gluon/05-moe-bmm1-fused-gather.py`:
    `test_op[128-c0]`

Target:
  NVIDIA GB300

Issue:
  `matrixVectorProd` rebuilt some disjoint LinearLayout contributions as
  separate shifts even when the same bit pattern can be represented exactly as
  one integer multiply. LinearLayout basis columns combine over GF(2); when the
  touched output rows are disjoint, xor, or, and integer addition agree bit for
  bit.

Dgrad shifted-basis run:
  The real lane-layout columns include:
    2064, 4128, 8256, 128, 256, 512, 1024
  The first three columns are shifted copies of one seed:
    2064 = 0x810
    4128 = 0x810 << 1
    8256 = 0x810 << 2

Before PTX:
  and.b32    %r270, %r1, 7;
  shl.b32    %r271, %r270, 11;
  shl.b32    %r272, %r1, 4;
  and.b32    %r273, %r272, 2032;
  or.b32     %r274, %r271, %r273;

After PTX:
  and.b32    %r270, %r1, 7;
  shl.b32    %r271, %r1, 4;
  and.b32    %r272, %r271, 1920;
  mad.lo.s32 %r273, %r270, 2064, %r272;

After SASS:
  LOP3.LUT R86, R14, 0x780, RZ, 0xc0, !PT;
  IMAD     R135, R85, 0x810, R86;

  For `s = x & 7`, the three shifted basis columns touch rows
  `{4, 5, 6, 11, 12, 13}`. Those rows are pairwise disjoint, so
  `(s0 ? 0x810 : 0) xor (s1 ? 0x1020 : 0) xor (s2 ? 0x2040 : 0)`
  is exactly `s * 0x810`.

Wgrad matching left shifts:
  The real matrix has two surviving left-shift terms with the same input mask.

Before PTX:
  and.b32    %r336, %r1, 24;
  shl.b32    %r337, %r336, 10;
  shl.b32    %r338, %r324, 4;
  shl.b32    %r339, %r336, 2;
  or.b32     %r344, %r337, %r338;
  or.b32     %r345, %r343, %r339;
  xor.b32    %r346, %r345, %r344;

After PTX:
  and.b32    %r335, %r1, 24;
  mul.lo.s32 %r336, %r335, 1028;
  shl.b32    %r337, %r323, 4;
  xor.b32    %r342, %r336, %r337;
  xor.b32    %r343, %r342, %r341;

After SASS:
  IMAD R7, R7, 0x404, RZ;

  For `x = (%r1 & 24)`, `x` can only contain bits 3 and 4.
  Therefore `x << 10` occupies bits 13 and 14 while `x << 2`
  occupies bits 5 and 6, so `(x << 10) | (x << 2)` is exactly
  `x * (1024 + 4)`.

Dgrad matching mixed shifts:
  A later real dgrad lane-layout matrix keeps two surviving terms with the
  same input mask but opposite shift directions.

Before PTX:
  shr.u32    %r281, %r266, 1;
  shl.b32    %r282, %r270, 4;
  shl.b32    %r283, %r266, 6;
  xor.b32    %r287, %r281, %r282;
  or.b32     %r288, %r285, %r283;
  xor.b32    %r289, %r287, %r288;

After PTX:
  shr.u32    %r281, %r266, 5;
  mul.lo.u32 %r283, %r281, 2064;
  shl.b32    %r282, %r270, 4;
  xor.b32    %r287, %r283, %r282;
  xor.b32    %r289, %r287, %r285;

After SASS:
  IMAD R141, R143, 0x810, RZ;

  Here `%r266 = %tid.x & 96`, so it only carries bits 5 and 6. For
  `s = %r266 >> 5`, the original right-shift term is `s << 4` and the
  left-shift term is `s << 11`. Their output rows are disjoint, so
  `(s << 4) xor (s << 11)` is exactly `s * (16 + 2048)`.

MoE reversed one-hot run:
  `_bitmatrix_metadata_compute_stage2` has a real shared-memory address
  layout with basis columns:
    64, 32, 16, 8, 4, 320, 128
  The first five columns map consecutive input bits to descending output rows.
  `brev` followed by a right shift computes those five one-hot contributions
  exactly in one term.

Before PTX:
  shl.b32    %r93, %r31, 6;
  shl.b32    %r94, %r29, 4;
  shl.b32    %r95, %r19, 2;
  shr.u32    %r96, %r23, 2;
  and.b32    %r97, %r25, 320;
  shl.b32    %r98, %r27, 1;
  or.b32     %r99, %r96, %r95;
  or.b32     %r100, %r99, %r21;
  or.b32     %r101, %r100, %r94;
  xor.b32    %r102, %r97, %r93;

After PTX:
  brev.b32   %r93, %r10;
  shr.u32    %r94, %r93, 25;
  and.b32    %r95, %r94, 124;
  and.b32    %r96, %r10, 64;
  shl.b32    %r97, %r96, 1;
  and.b32    %r98, %r10, 32;
  mul.lo.s32 %r99, %r98, 10;
  xor.b32    %r100, %r95, %r99;
  or.b32     %r101, %r100, %r97;

After SASS:
  BREV R12, R3;
  SHF.R.U32.HI R14, RZ, 0x19, R12;

  For input bit `i` in `[0, 4]`, `brev` places it at bit `31 - i`.
  Shifting right by 25 moves it to bit `6 - i`, matching the five basis
  columns bit for bit. The lowering only uses this form for reversed one-hot
  runs, and still XORs the resulting term when any output row is shared by
  another basis column.

MoE reversed four-bit run:
  The same checked-in stage2 specialization has a second address layout with
  basis columns:
    320, 32, 16, 8, 4, 128, 64
  Columns one through four map input bits one through four to output bits five
  through two, so `brev(x & 30) >> 25` is exact for that contiguous run too.

Before PTX:
  shl.b32    %r106, %r31, 4;
  shl.b32    %r107, %r19, 2;
  shr.u32    %r108, %r23, 2;
  add.s32    %r110, %r100, %r108;
  add.s32    %r111, %r110, %r107;
  add.s32    %r112, %r111, %r21;
  add.s32    %r113, %r112, %r106;

After PTX:
  and.b32    %r106, %r10, 30;
  brev.b32   %r107, %r106;
  shr.u32    %r108, %r107, 25;
  add.s32    %r113, %r100, %r108;

  For input bit `i` in `[1, 4]`, `brev` places it at bit `31 - i`.
  Shifting right by 25 moves it to bit `6 - i`, matching output bits five
  through two. Masking before `brev` removes every input bit outside that run,
  so the replacement is bitwise exact for all 32-bit inputs.

MoE sparse anti-diagonal:
  The same stage2 specialization also has a sparse one-hot anti-diagonal:
    input bit 0 -> output bit 6
    input bit 1 -> output bit 5
    input bit 3 -> output bit 3
  These selected basis columns share `input_bit + output_bit == 6`, so masking
  the reversed source exactly reconstructs the same layout contribution.

Before PTX:
  and.b32    %r165, %r10, 11;
  prmt.b32   %r166, %r165, 0, 0x7701U;
  cvt.u16.u32 %rs13, %r166;
  ...
  shr.u16    %rs23, %rs22, 9;
  cvt.u32.u16 %r167, %rs23;

After PTX:
  brev.b32   %r165, %r10;
  shr.u32    %r166, %r165, 25;
  and.b32    %r167, %r166, 104;

  For every 32-bit input `x`,
    (brev(x) >> 25) & 0x68
  maps exactly bits zero, one, and three to outputs six, five, and three, and
  masks every other bit away.

MoE explicit multi-bit columns:
  The same stage2 specialization has explicit columns that map one input bit to
  a multi-bit output basis:
    input bit 5 -> output basis 320
    input bit 6 -> output basis 320
  The old explicit-column lowering selected either zero or the basis constant,
  which `ptxas` materialized through a signed one-bit mask even though the same
  input bit was already needed in unsigned 0/1 form.

Before PTX:
  and.b32    %r25, %r10, 32;
  bfe.s32    %r26, %r10, 5, 1;
  bfe.u32    %r27, %r10, 5, 1;
  ...
  and.b32    %r67, %r26, 320;

Hand-mutated PTX candidate:
  and.b32    %r25, %r10, 32;
  bfe.u32    %r27, %r10, 5, 1;
  ...
  mul.lo.u32 %r67, %r27, 320;

After source lowering:
  and.b32    %r25, %r10, 32;
  bfe.u32    %r26, %r10, 5, 1;
  ...
  mul.lo.s32 %r64, %r26, 320;

After SASS:
  SHF.R.U32.HI R7, RZ, 0x5, R0;
  SGXT.U32     R7, R7, 0x1;
  IMAD         R15, R7, 0x140, RZ;

  For explicit input column `i`, `bit = x & (1 << i)` is always either zero or
  `1 << i`. Therefore the previous `bit == 0 ? 0 : basis` is exactly
  `(bit >> i) * basis` for every 32-bit input. The new lowering keeps the
  already-normalized 0/1 spelling available for other users and avoids the
  signed-mask form.

Effect:
  Hand-editing the emitted PTX first and assembling it with CUDA 13.1 `ptxas`
  reduced final SASS instruction lines from 10911 to 10909 for the dgrad
  shifted-run case. For the wgrad left-shift case, the same workflow reduced
  final SASS instruction lines from 6802 to 6794. For the dgrad mixed-shift
  case it reduced final SASS instruction lines from 4320 to 4312 and the cubin
  size from 220952 to 220704 bytes. For the MoE reversed-run case it reduced
  final SASS instruction lines from 400 to 392; the four-bit stage2 case reduced
  final SASS instruction lines from 752 to 736 and the cubin size from 35616 to
  35112 bytes. For the sparse anti-diagonal case it reduced executable SASS
  lines from 800 to 784 and cubin size from 37120 to 36480 bytes. For the
  explicit multi-bit-column case, the source-replayable lowering reduced the
  current checked-in MoE stage2 SASS from 331 to 323 lines and cubin size from
  33488 to 33040 bytes. Compiling the checked-in specializations from source
  after the lowering change emits the same multiply and `brev` forms in PTX and
  SASS.
